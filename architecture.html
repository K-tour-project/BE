01 PROJECT프로젝트 개요

백엔드가 무엇을 하는 서버인지, 사용자는 어떻게 쓰는지.

🖥️ 백엔드 한 줄 정의

"어떤 작품이 어디서 촬영됐는지" 데이터를 관리하고, 그걸로 검색·지도·코스 추천을 제공하는 서버.

📱 사용자 흐름

작품/지역 검색 → 지도에 촬영지 마커 → 장소 여러 개 선택 → 관광 동선 추천 → 코스 저장. (챗봇은 팀원 담당)

02 WHY핵심 컨셉 — 왜 이렇게 설계했나

이 한 가지가 설계 전체의 출발점이에요.

⭐ TourAPI엔 "작품 ↔ 촬영지" 연결이 없다
한국관광공사 TourAPI는 관광지 정보(좌표·주소)는 주지만, "도깨비가 주문진 방파제에서 촬영됨" 같은 작품-장소 연결 데이터는 없습니다. 그래서 그 연결을 우리가 직접 큐레이션해서 DB에 만드는 것이 이 앱의 차별점이자 데이터베이스의 심장(content_place_mappings 테이블)입니다.

03 STACK기술 스택 (신입용 한 줄 설명)

각 도구가 무슨 역할인지 쉬운 말로.

⚡ FastAPI

파이썬 웹 프레임워크. 요청을 받아 응답을 돌려주는 서버를 빠르게 만듦. 비동기에 강하고 API 문서가 자동 생성됨.

🐘 PostgreSQL + PostGIS

데이터를 표 형태로 저장하는 관계형 DB + 지도 좌표·거리·반경 계산을 해주는 공간 확장(PostGIS).

🔗 SQLAlchemy (async)

ORM — 파이썬 클래스(객체)와 DB 테이블을 자동으로 연결. SQL을 직접 안 짜도 파이썬으로 DB를 다룸.

🧬 Alembic

마이그레이션 도구. DB 테이블 구조 변경을 코드로 기록·적용(= DB의 git 같은 버전 관리).

🔐 자체 JWT + 소셜

로그인 후 발급하는 토큰(JWT)으로 "이 요청이 누구인지" 인증. 구글·카카오 소셜 로그인 지원.

🌐 httpx

서버에서 외부 API(TourAPI)를 호출하는 비동기 HTTP 클라이언트.

요청이 어디서 와서 어디를 거쳐 처리되는지 큰 그림.

📱

🤖

↓ HTTP 요청 (REST API)
⚡

↓ SQLAlchemy
🐘
PostgreSQL + PostGIS우리 데이터 7개 테이블 (좌표·작품·연결·코스)
↔ httpx · 실시간
🏛️
KTO TourAPI관광지 상세 (저장X, 매번 호출)
💡 신입 포인트 — "계층(layer)"으로 나누는 이유
주소를 받는 라우터, 실제 일을 하는 서비스, DB를 다루는 모델을 나눠두면 — 코드가 섞이지 않아 고치기·테스트하기 쉬워집니다. (역할 분리 = 유지보수의 기본)

05 FLOW요청 흐름 예시 — "도깨비" 검색 → 코스 저장

실제 한 번의 사용이 백엔드 안에서 어떻게 흐르는지.

  1. 사용자가 "도깨비"를 검색 → 앱이 백엔드로 요청을 보냄
  2. 백엔드가 contents에서 작품을 찾고, content_place_mappings로 연결된 촬영지(places)를 조회
  3. 각 장소의 좌표(geom)를 지도 마커로, 포스터(poster_url)를 함께 응답
  4. 장소 상세(운영시간 등)는 TourAPI를 실시간 호출해서 채움 무캐싱 규칙
  5. 사용자가 장소 여러 개를 골라 → 백엔드가 좌표로 최적 동선을 계산해 코스 추천
  6. 로그인 사용자가 저장하면 → courses + course_places(순서)에 기록

테이블별 역할 & 컬럼

테이블역할핵심 컬럼 의미
users회원(구글·카카오)auth_provider+provider_user_id 조합으로 같은 계정 중복가입 방지
contents작품(영화·드라마)title_ko=검색 대상, poster_url=이미지 URL(저장X 표시O)
regions지역코드area_code=TourAPI 코드, centroid=지역 검색 시 지도 중심
places장소geom=좌표(마커·거리계산), tour_content_id=TourAPI 연결키
content_place_mappings ★작품↔장소 연결"이 작품이 이 장소에서 촬영" 한 줄 = 앱의 핵심 자산
courses저장 코스user_id=주인, created_at=저장일
course_places코스 경유지visit_order=방문 순서(1,2,3…)

컬럼별 상세 역할

7개 테이블의 모든 컬럼이 각각 무슨 일을 하는지. PK 고유번호 · FK 다른 표 연결 · ENUM 정해진 값 · GEO 좌표

👤 users — 회원(구글·카카오 로그인)

컬럼종류역할 (쉬운 설명)
user_idPK회원 한 명을 가리키는 고유 번호 (자동 증가)
nickname—화면에 보여줄 별명/이름
auth_providerENUM어떤 소셜로 로그인했는지 (google / kakao)
provider_user_id—구글·카카오가 그 사람에게 부여한 고유 ID. auth_provider와 묶어 같은 사람을 식별 → 중복가입 방지

📍 regions — 지역(검색용 시드)

컬럼종류역할 (쉬운 설명)
region_idPK지역 한 곳을 가리키는 고유 번호
area_code—한국관광공사 TourAPI가 쓰는 지역 코드(예: 강원=32). 외부 호출 시 사용
name—지역 이름 (예: 강릉시)
centroidGEO그 지역의 지도 중심 좌표. 지역을 검색하면 지도를 이 위치로 이동

🎬 contents — 작품(영화·드라마)

컬럼종류역할 (쉬운 설명)
content_idPK작품 한 편을 가리키는 고유 번호
content_typeENUM영화/드라마/예능 구분 (movie / drama / show)
title_ko—한국어 제목 → 검색의 주 대상
poster_url—포스터 이미지 링크(URL). 이미지를 저장하지 않고 주소만 보관 (다운로드 금지 규칙)

🗺️ places — 장소(촬영지)

컬럼종류역할 (쉬운 설명)
place_idPK장소 한 곳을 가리키는 고유 번호
name—장소 이름 (예: 주문진 방파제)
geomGEO장소 좌표 → 지도 마커 표시 + 거리·반경 계산
region_idFK이 장소가 속한 지역(→ regions). 지역이 삭제되면 이 값만 비워짐
tour_content_id—TourAPI가 그 관광지에 부여한 ID. 장소 상세를 실시간으로 불러올 때 연결 열쇠

⭐ content_place_mappings — 핵심: 작품↔장소 연결

컬럼종류역할 (쉬운 설명)
mapping_idPK연결 한 줄을 가리키는 고유 번호
content_idFK어떤 작품인지 (→ contents)
place_idFK어떤 장소인지 (→ places)
한 줄 = "이 작품이 이 장소에서 촬영됨". (content_id, place_id)는 유니크라 같은 조합이 두 번 안 들어감. TourAPI엔 없는 데이터라 우리가 직접 채우는 앱의 심장.

🧳 courses — 사용자 저장 코스

컬럼종류역할 (쉬운 설명)
course_idPK저장된 코스 하나를 가리키는 고유 번호
user_idFK이 코스의 주인(→ users). 회원이 탈퇴하면 그 코스도 함께 삭제
title—코스 이름 (예: "도깨비 강릉 여행")
created_at—코스를 저장한 시각

🧭 course_places — 코스 경유지(순서)

컬럼종류역할 (쉬운 설명)
course_place_idPK경유지 한 줄을 가리키는 고유 번호
course_idFK어느 코스에 속하는지(→ courses). 코스가 삭제되면 함께 삭제
place_idFK어떤 장소인지(→ places). 코스에 담긴 장소는 함부로 삭제 못 함
visit_order—방문 순서 (1,2,3…). (course_id, visit_order) 유니크 → 같은 코스에서 순서 중복 방지

07 RULES공모전 제약 → 설계 반영

실격을 피하려고 규칙을 DB 구조에 못박았습니다.

공모전 규칙설계에 어떻게 반영했나
TourAPI 실시간 호출 + 입증호출 기록 테이블 api_call_logs (4단계에서 활성화) ⚠️
API 응답 무캐싱places에 운영시간·이미지를 저장하지 않음 → 매번 실시간 호출
인증키 서버 전용 / 이미지 URL만키는 서버에만, 이미지는 URL 문자열만 보관
GPS 미저장 / 반경 20km코스는 좌표 대신 place_id로 참조
금지 API(areaCode2)regions를 고정 시드 테이블로 미리 보유
⚠️ 합격 핵심
"TourAPI를 실시간으로 호출하고 그걸 api_call_logs로 입증" — 이게 안 되면 심사 제외예요. 4단계에서 반드시 구현.

09 GLOSSARY신입 개발자용 용어 사전

이 문서에 나온 용어를 쉬운 말로.

API / REST
프로그램끼리 약속된 형식으로 데이터를 주고받는 창구. REST는 그 약속의 한 방식(주소+HTTP).
ORM
DB 테이블을 파이썬 객체(클래스)처럼 다루게 해주는 도구. SQL을 직접 안 짜도 됨.
마이그레이션(Migration)
DB 테이블 구조를 바꾼 이력을 코드로 남기고 적용하는 것. "DB의 버전 관리".
PK / FK
PK=각 줄의 고유 번호. FK=다른 테이블의 PK를 가리키는 연결고리.
ENUM
정해진 값만 허용하는 타입(예: movie/drama/show). 오타·잘못된 값을 DB가 막아줌.
비동기(async)
외부 API를 기다리는 동안 다른 일을 처리. 여러 요청을 효율적으로 동시 처리.
JWT
로그인 후 받는 출입증 토큰. 매 요청에 첨부하면 서버가 "누구인지" 확인.
PostGIS / geography
PostgreSQL에 좌표·거리·반경 계산 기능을 더한 확장. geom이 그 좌표 타입.
인덱스(Index)
검색을 빠르게 하는 "책 색인". 예: 지도 좌표 검색용 공간 인덱스(GIST).
M:N (다대다)
한 작품이 여러 장소, 한 장소에 여러 작품 → 중간 연결 테이블이 필요(=핵심 자산).
